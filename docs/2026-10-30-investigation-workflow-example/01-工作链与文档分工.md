# Investigation Workflow — 工作链与文档分工

```yaml
doc_type: REFERENCE
lifecycle: ACTIVE
knowledge_state: INFERRED # 行为来自已复盘的来源案例；成功原因为解释，非控制实验结论
date: 2026-10-30
authority: 示例层 DOCS reference；不是 repository policy
```

## 工作链

| 环节 | 要回答的问题 | 主要产出 | Authority |
|---|---|---|---|
| 1. 用户目标 | 用户真正需要的能力是什么？非目标和授权边界是什么？ | Topic Summary 的目的 / 范围 / 非目标 | DOCS（用户决定以原话或日期记录） |
| 2. 当前差距 | 现状（baseline）与目标之间缺什么？ | baseline audit、target 定义 | DOCS |
| 3. 整体路线 | 哪些已知、哪些要实验、哪些要用户决定？ | Pipeline Design；FEV Root Question 与 Sub-FEV 拆分 | DOCS（handoff 前）→ Graph（handoff 后） |
| 4. 局部实验 | 当前最能减少不确定性、依赖已满足的问题是什么？ | Sub-FEV Run、Local Verdict | Pipeline Run |
| 5. 回填 | 结果改变了路线、设计或先前结论吗？ | 更新 design、Evidence Analysis、Topic Summary、aggregate | DOCS + Graph |
| 6. 下一项 | 授权内的下一项有价值工作是什么？ | 下一阶段的输入 | — |
| 7. Promotion | feasibility 问题已经回答了吗？用户批准进入业务吗？ | Promotion Recommendation → Human `APPROVED` → OpenSpec change | OpenSpec |
| 8. Production ICD | production 实现是否独立满足 Capability？ | 独立 Acceptance Graph、L1–L4 Evidence | ICD |

第 4–6 步会多次循环。一个 stage 不一定对应一个 Sub-FEV；按 independently testable uncertainty 拆分。

## Topic 文档分工骨架

开始调查时先建立下面的分工，并在 Topic Summary 中给出索引。文件编号和数量按实际用途定；没有内容的文件不要创建。

| 文件（示例） | 职责 | 何时更新 |
|---|---|---|
| `00-调研总览.md` | 当前结论、knowledge state、关键 Evidence、下一步、文档索引 | 每次有新事实或新决定之后 |
| `01-*-baseline.md` | 现状 audit：已有资产、能力、已知限制 | 发现 baseline 与预期不同时 |
| `02-*-target.md` | 目标能力、非目标、验收口径 | 用户修正目标时（必须同步 design 与 Graph contract） |
| `03-*-design.md`（`PIPELINE_DESIGN`） | 路线、stage、输入 / 输出、依赖 | 实验结果改变路线或上游时 |
| `04-*-evidence.md`（`EVIDENCE_ANALYSIS`） | Observation / Interpretation / Conclusion / Unknown；引用 stable Run identity | 每个有意义的 stage 结束时 |
| `05-*-promotion.md` | Promotion Recommendation、用户决定及其日期 | feasibility 已回答时 |

FEV Graph 的 aggregate report 持有 Root Verdict；Topic 只引用它，不复制 Run output。

具体例子：[Example Character Topic](../2026-10-30-example-character-blender-ue5/00-调研总览.md) 使用 `01-Baseline与Target`、`02-Pipeline设计`、`03-FEV-Evidence分析`、`04-Promotion-Recommendation` 四个文件。

## 成功因素

以下解释有来源记录支持，但不是因果证明。

| 因素 | 具体做法 | 可复用条件 |
|---|---|---|
| 目标决定实验 | 用户把宽泛的技术清单收窄为少数核心能力后，同步修改 design、contract 与 config | 开始时和范围变化时都重新核对目标，不能只维护技术任务表 |
| 文档职责提前分好 | 初始 plan 就安排了 baseline、target、design、analysis 与回填 | 复用职责划分，不要求相同文件名 |
| 每项实验产生下一步输入 | 映射表、seed、导出文件、state plan 等由下游 stage 读取 | 写清实际输入、输出、依赖与适用范围 |
| 失败在局部处理 | 普通错误修复、API probe、上游修正后重跑、换用仍满足目标的实现路径 | 替代路径仍满足用户意图；改变范围时请用户决定 |
| 结果同步到知识与设计 | 每个主要 stage 后更新 Topic 与 aggregate | 阶段完成包含知识更新，但不需要每次 tool call 都更新文档 |
| 具体结果支持具体选择 | 问用户时附上已完成的结果、推荐和影响 | 沿用已有授权，不为阶段名变化重复索取同一批准 |
| 交接后核对真实状态 | 接手的 Agent 发现 handoff 已过时：某 stage 已完成，旧 blocker 只在另一个环境存在 | 当前 artifact 优先于旧 handoff |
| FEV 到 production 的路径清楚 | 实验配置抽成 profile，业务模块重写，另建独立 ICD Graph，以 FEV canonical 作为参考数据 | 用户批准 Promotion；production 不 import FEV script |

## Human / Agent 分工

- **用户：** 修正核心目标与非目标；提供参考实现方向；选择主要 stage；要求关键 Evidence（例如真实 rendering）；决定命名与 seed；批准 Promotion。
- **Agent：** 建立并持续更新 artifact；设计并执行局部实验；处理普通故障；把下游发现反馈到上游并重跑依赖；解释结果并提出具体选择；获得广泛授权后连续完成 OpenSpec → 实现 → ICD。
- **环境：** 已有 launcher、cook runtime、lease、参考 Graph 和隔离 Worker（见 [AIAGENT session isolation](../../traits/aiagent-windows-session-isolation-trait.md)）。环境恢复也是推进的一部分。

handoff 中明确要求“先询问再执行”时，阶段之间的停顿属于用户的选择，不能算作 Agent 缺乏主动性。

## 不应泛化的做法

- 固定的文件数量、stage 编号或目录名。
- 每个阶段都询问用户；只有在用户要求 checkpoint 或需要真正的决定时才询问。
- 每个阶段都更新所有文档；只更新受影响的 artifact。
- 一次性重写全部 FEV 代码；按业务边界决定保留、重构或改写。
- 把一次研究流程的成功当作整个产品已交付；FEASIBLE 不自动成为 ICD PASS。
- 用不同任务的结果推断模型能力差异。
